# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

PSModuleMaintenance is a Windows-based automation tool that keeps PowerShell modules up to date. It uses Microsoft.PowerShell.PSResourceGet to update modules and prune old versions on a weekly schedule.

## Requirements

- Windows 10/11 or Windows Server 2019+
- PowerShell 7.0+
- Microsoft.PowerShell.PSResourceGet module. A hard dependency (`#Requires -Modules`), but bundled with PowerShell 7.4 and later under `$PSHOME\Modules`, so it normally needs no separate install. That bundled copy is not in the AllUsers module path, so `Get-PSResource` does not list it and this script neither updates nor prunes it: it moves only when PowerShell itself is updated

## Running the Scripts

```powershell
# Full maintenance (update + prune)
.\Invoke-PSModuleMaintenance.ps1

# Update only
.\Invoke-PSModuleMaintenance.ps1 -UpdateOnly

# Prune only
.\Invoke-PSModuleMaintenance.ps1 -PruneOnly

# Dry run
.\Invoke-PSModuleMaintenance.ps1 -WhatIf

# One-time OneDrive migration (requires Administrator)
.\Invoke-OneDriveMigration.ps1

# Install scheduled task (requires Administrator)
.\Install-ModuleMaintenance.ps1

# Uninstall scheduled task
.\Install-ModuleMaintenance.ps1 -Uninstall

# Run the tests (a few seconds, no network, no elevation)
.\tests\Invoke-Tests.ps1
```

## Tests

`tests\Invoke-Tests.ps1` runs every `tests\Test-*.ps1`, each in a process of its own. Run it after changing either script.

- **They run the real code.** `Get-ScriptFunctionText` in `TestHelpers.ps1` lifts a function out of a script through the PowerShell parser, so the script never has to run. A test stands in only for what would touch the network or the machine (`Invoke-ModuleUpdate`, `Find-PSResource`, `Write-Log`, `powershell.exe`)
- **They are plain scripts, not Pester.** Deliberate: no dependency on a module this tool itself updates. Do not name a file `*.Tests.ps1`, or Pester will try to discover it
- **Variable names collide with the `-Quiet` switch.** Every test file declares `param([switch]$Quiet)`, and PowerShell names are not case-sensitive, so `$quiet = @()` inside a test fails with a conversion error
- **The migration script is tested as a whole**, because it is one long script and not a set of functions. `Test-Migration.ps1` runs a copy of it in which three lines are replaced: the demand for elevation, the user's module folder and the AllUsers module folder. The copy is checked before it runs, and carries a guard that stops it before the first write unless both folders lie inside the temp folder. If the script changes so that one of the three lines is no longer found, the test stops instead of running against real folders
- **`$env:ProgramFiles` cannot be redirected for a child process.** Windows sets it afresh for every process it starts, so the child sees the real folder whatever the parent put there. `$env:OneDrive` is an ordinary variable and is inherited. This was found the safe way: the guard refused to run. A path under Program Files has to be replaced in the text
- **`Get-PSResource` is an alias, and an alias is found before a function.** The PSResourceGet module gives `Get-InstalledPSResource` the alias `Get-PSResource`. Command lookup goes alias, function, cmdlet, so a stand-in function named `Get-PSResource` is passed over as soon as the module is loaded, and the code under test sees the modules of the machine it runs on. `Update-PSResource`, `Install-PSResource`, `Uninstall-PSResource` and `Find-PSResource` are real cmdlet names, which a function does shadow. This was found when a whole-script test listed the real modules; nothing was changed, because the commands that change things were shadowed, but a test must not depend on that. A process that runs the whole script therefore loads the module first, removes its aliases (`Remove-Alias -Scope Global`), defines the stand-ins and only then checks them
- **`#Requires -Modules` finds `Import-Module` by name**, so a stand-in for `Import-Module` receives that call too, with parameters such as `-Version`. A stand-in for it has to pass everything on to `Microsoft.PowerShell.Core\Import-Module` except the one module it is there to keep out
- **`Test-ConfigFault.ps1` runs the whole main script.** What it tests is what the main block does and does not call, and the main block is not a function. Every call that could change the machine or reach the network is a stand-in that only writes down that it was called
- **A test that removes or installs checks its stand-ins first.** `Test-KeepVersions.ps1` runs the real `Remove-OldModuleVersions` and `Update-AllModules`, so it verifies that `Uninstall-PSResource`, `Get-PSResource`, `Invoke-ModuleUpdateWithRetry` and `Find-GalleryModules` resolve to functions before anything is called, and stops if one does not
- **They cover the fault paths**, which a normal run almost never reaches: network faults, an unreachable gallery, a module owned by another program. A healthy weekly run proves nothing about these, so the tests are the only evidence they still work
- **This is a public repository.** A test must not contain anything from a real machine: no user or machine name, no paths under a user profile, no organisation, no network names, nothing read from the real log folder. Recorded error messages are embedded with the module name replaced (`Contoso.Tools`), and the machine name is fixed to `TEST-HOST` inside the test. The same goes for examples in the docs and for commit messages
- A new stand-in for `Find-PSResource` must raise errors with the same `-ErrorId` as the real cmdlet (`PackageNotFound`, `HttpRequestCallFailure`), because `Find-GalleryModules` classifies by id

## Architecture

**Invoke-PSModuleMaintenance.ps1** - Main maintenance script with six sections:
1. Configuration - Loads `config.json`, merges with defaults
2. Logging - Initializes log files, transcript, and summary tracking. `Get-SummaryFailures` is the single definition of "the run had failures"
3. Toast Notifications - `Send-ToastNotification` function (shells out to PS 5.1 for WinRT support)
4. Healthchecks Monitoring - `Get-HealthchecksUrl`, `Format-HealthchecksBody`, and `Send-HealthchecksPing` (dead-man's-switch pings to Healthchecks.io)
5. Self-Checks - `Test-ScheduledTaskHealth` (warns when the scheduled task launches a hard-coded interpreter path)
6. OneDrive Utilities - `Test-OneDrivePath`, `Test-ManagedModuleFolder`, `Resolve-ModuleVersionFolder` and `Remove-LockedModuleFolder` functions (used for scope detection, telling our modules from another program's, finding where a version really is, and locked-file fallback during updates/pruning)
7. Module Operations - version helpers (`ConvertTo-NormalizedVersion`, `Get-ModuleVersionKey`, `ConvertFrom-PinnedVersionString`, `Get-PinnedVersion`, `Test-IsPinnedVersion`), the KeepVersions helpers (`ConvertFrom-KeepVersionSelector`, `Test-KeepVersionMatch`, `Get-KeepVersionSelectors`, `Get-KeepVersionRange`) and the two pure planning functions (`Get-ModulePrunePlan`, `Get-KeptLinePlan`), plus `Invoke-ModuleUpdate`, `Get-TransientNetworkFault`, `Invoke-ModuleUpdateWithRetry`, `Set-PinnedModuleVersions`, `Find-GalleryModules`, `Get-GalleryFaultText`, `Update-KeptVersionLines`, `Update-AllModules`, `Confirm-KeptModuleVersions`, and `Remove-OldModuleVersions`
8. Main Execution - Orchestrates the workflow with try/finally for cleanup and incremental summary saves

**Invoke-OneDriveMigration.ps1** - Standalone one-time script that migrates modules from OneDrive-synced CurrentUser path to AllUsers scope, then cleans up OneDrive copies. Self-contained with its own copies of `Test-OneDrivePath`, `Test-ManagedModuleFolder`, `Remove-LockedModuleFolder`, and `Write-Log`. Requires Administrator. Only migrates modules PSResourceGet installed; anything else is logged as left in place and is excluded from the cleanup phase too. **An original is only deleted once the same version exists in AllUsers**: the cleanup used to remove every version folder whether or not its copy had succeeded, so a copy that did not succeed lost the module from both places while the run ended with "completed" at SUCCESS. Under `-WhatIf` nothing reaches AllUsers, so the dry run goes by the list of versions it would have copied instead of by what is on disk.

**Install-ModuleMaintenance.ps1** - Creates Windows Scheduled Task that runs the maintenance script weekly as the current user with elevated privileges.

**config.example.json** - The tracked template, holding exactly the built-in defaults. `tests\Test-Config.ps1` fails if it drifts from them, stops validating against the schema, or stops being neutral (Healthchecks off, nothing excluded, pinned or kept).

**config.json** - The settings of one installation. **Ignored by git, and optional**: without it the script runs on its built-in defaults. Validated against `config.schema.json`:
- `ExcludedModules`: Array of module names to skip
- `PinnedModules`: Object mapping module name to an exact version to hold (default `{}`)
- `KeepVersions`: Object mapping module name to a list of version prefixes, each naming an older line to keep and update next to the newest version (default `{}`)
- `LogRetentionDays`: How long to keep logs (default 180)
- `TrustPSGallery`: Trust repository during updates (default true)
- `NotificationMode`: Toast notifications — `Always` (default), `OnFailure`, or `Never`
- `ModuleUpdateTimeoutSeconds`: Per-module update timeout in seconds (default 600)
- `Healthchecks`: Object — `Enabled` (default false), `SecretName`, `SecretVault`, `TimeoutSeconds`. The ping URL itself is **never** stored here; it lives in the SecretManagement vault

## Key Implementation Details

- **Version pinning**: `PinnedModules` holds a module at one version. `Set-PinnedModuleVersions` runs first in the update phase and installs the pinned version via `Install-PSResource` when it's missing (a bare version string is a *required* version in PSResourceGet, not a minimum — see `about_PSResourceGet`, "NuGet version ranges"). Pinned modules stay in the `Find-PSResource` bulk query (same single call either way) so the log can report `<module> is pinned to <pin> — holding back <gallery>` and record it in `Summary.PinsHoldingBack`; they are filtered out of the update loop immediately after. In `Remove-OldModuleVersions` a pinned module keeps the pin instead of the newest version, so newer versions get pruned. **Safety invariant**: if the pinned version isn't installed, that module is pruned not at all — otherwise a bad pin would delete every version. Versions are compared via `Get-ModuleVersionKey` (4-part normalization + prerelease label), so `2.19`, `2.19.0`, and `2.19.0.0` are the same pin. Exclusion beats pinning: a module in both lists is dropped from `PinnedModules` at config load with a warning
- **Kept version lines**: `KeepVersions` keeps an older line of a module next to its newest version, and keeps both current. It is the third per-module exception and the only one that does both: exclusion freezes the module, a pin holds one version and prunes the rest. A selector is a version *prefix* (`"5"`, `"5.7"`), and a line is everything that starts with it
    - **Two pure functions hold the rules**: `Get-ModulePrunePlan` (what stays, what goes) and `Get-KeptLinePlan` (which lines need a lookup). No logging, no script state. Keep them that way: they are the only reason pruning and pinning are testable at all without standing in for PSResourceGet
    - **Pruning keeps** the newest version, or the pin, plus the newest installed version of each line. The pin-missing safety rule is unchanged. A version that stays is never removed even when it is listed twice (the same version can sit in two scopes), which the older logic got wrong
    - **Selectors have their own strict parser.** `[version]` cannot parse `5`, and it accepts things a selector must not be. Only a quoted string counts: JSON reads an unquoted `5.10` as the number 5.1, which would select another line without a word
    - **Matching is number by number**, against the normalized version. `"1"` does not match 12.4.0, `"5.7"` does not match 5.70.1. Never compare as text
    - **The line update runs BEFORE the normal update loop.** `Update-AllModules` returns early when no module needs updating, which is most weeks. Placed after the loop it would almost never run
    - **"Covered by the normal update" is judged from the gallery, not from what is installed.** With only an old line installed, that line looks like the newest one; skipping it would leave it a release behind for good. The line is skipped only when the gallery's newest release is in it, the newest installed version is in it, and the module is not pinned (the normal update drops pinned modules)
    - **The gallery is asked with a NuGet range**, `-Version '[5.0.0.0, 6.0.0.0)'`, through `Find-GalleryModules -Version`, one call per module spanning its lines. **Never a wildcard**: `'5.*'` was seen returning versions from the line above. A range with nothing in it returns nothing and raises **no** error, not even `PackageNotFound`, so an empty answer is an answer
    - **A line is only maintained once a version of it is installed.** Nothing installed for a selector is a WARN and nothing more: no install, and the run still counts as successful. That was a deliberate choice, do not "fix" it by installing
    - **Only stable releases are targets.** A line update never installs a prerelease. Comparison is by number only, as in the normal update, so an installed prerelease with the same number as the stable release is not replaced
    - **A pin inside a kept line decides**: that line is not updated. A line outside the pin updates normally
    - **Counting**: a failed line update goes into `ModulesFailed` (with `Line` and `Version`) and counts under `Updates`. A line lookup without an answer goes into `KeepLinesUnchecked` and shares the one `Lookups` count with `ModulesUnchecked`. `KeepVersionsUnmatched` feeds nothing. Once the gallery fails to answer, the remaining lines are recorded as not checked instead of being asked one by one
    - **The WARN for an unmatched selector needs its own pass**, `Confirm-KeptModuleVersions`. The prune loop only looks at modules with more than one installed version, so a module with a single version would never be looked at. It runs in the prune phase, after the updates
    - **Rollout order matters when a module moves from `ExcludedModules` to `KeepVersions`.** An older script ignores the unknown setting, so the module would simply stop being excluded and its old line would be pruned. Code first, config last
- **A config file that cannot be read stops the run before any module is touched.** `Import-MaintenanceConfig` sets `$script:ConfigFault`, and the main block then skips the update phase, the prune phase and the log cleanup. Going on would mean running on the built-in defaults, under which nothing is excluded, pinned or kept, so every module would be updated and every old version pruned, including the ones the file was written to protect. This was the owner's decision: be cautious rather than default to pruning
    - **Updating is as unsafe as pruning here.** On defaults an excluded module would be updated and a pinned one moved past its pin. That is why the run stops altogether and does not merely skip the prune
    - **Log retention comes from the same file**, so old logs are left alone too
    - **It used to be invisible.** The message went to `Write-Warning`, which nobody sees in a scheduled task, and the run carried on as if nothing had happened
    - **Only an unreadable file counts.** A file that does not exist means the defaults are what was asked for. A single entry that is not understood (a bad pin, a bad selector) is a WARN about that entry and the run goes on. Note what that means: the module the entry was about is then treated like any other, and its old versions are pruned
    - **Monitoring without a config**: whether Healthchecks is on is in that file too. `Get-HealthchecksUrl -WithoutConfig` looks for the secret under the name and vault in force, which are the defaults, and the run sends a Fail ping if it finds one. No start ping. A secret that is not there is an INFO line, not a WARN: monitoring may never have been set up
    - It counts as one failure (`Get-SummaryFailures` reports `Config` as 0 or 1), and the toast says what happened instead of "Updated 0 modules"
- **`config.json` is not in the repository.** It used to be tracked, which published the settings of one installation and showed every local edit as a change. Two things follow:
    - **The scheduled task runs from the working folder and reads that file.** If it goes missing the run still works, but on defaults: Healthchecks is then off, so no ping is sent and the check goes overdue. Treat a missing `config.json` on a configured machine as a fault, not as a clean state
    - **Git deletes a file from the folder when it stops being tracked, and overwrites an ignored file without asking.** Any checkout, merge or pull that crosses the commit which removed `config.json` can take the local file with it. Back it up before such an operation and compare afterwards. The safe way to publish a commit without touching the folder is to push the branch straight to `main` and move the local `main` with `git branch -f`, instead of switching and merging
    - A change to the defaults has to be made in three places: `$script:Config` in the script, `config.schema.json` and `config.example.json`. The test compares the first and the last
- **Config warnings before logging exists**: `Import-MaintenanceConfig` runs before `Initialize-Logging`, so pin validation problems are queued in `$script:ConfigWarnings` and written to the log as WARN once logging is up
- **Per-module timeout**: Each `Update-PSResource` call runs in an isolated PowerShell runspace via `Invoke-ModuleUpdate`. If a module exceeds `ModuleUpdateTimeoutSeconds` (default 600s), the script gives up on it and moves to the next — prevents one slow/hung module (e.g. Microsoft.Graph) from consuming all scheduled task time. **The obvious implementation of this does not work**, and both traps were measured, not guessed:
    - **`$ps.Stop()` blocks** until non-cooperative native work finishes. PSResourceGet's network and file I/O do not cooperate, so a timed-out module still ran to completion — a controlled repro took 20s against a 5s timeout. Use `BeginStop` with a short grace (`$stopGraceSeconds`, 5s), then abandon the runspace to the GC rather than `Dispose`-ing it, since disposing a still-winding-down runspace can block just as badly
    - **`AsyncWaitHandle.WaitOne` cannot be trusted as the completion signal.** It was observed returning `$true` while the pipeline was still running, after which `EndInvoke` silently absorbed the rest of the runtime and the module was logged as SUCCESS. In one run a large meta-module took more than twice the 600s timeout and still reported success, while every other module took a few seconds. The fix polls in 500ms slices against a `Stopwatch` and treats only a terminal `$ps.InvocationStateInfo.State` (`Completed`/`Failed`/`Stopped`) as done, so a spurious signal costs one extra lap instead of dropping out of the loop
    - **The runspace does not inherit `$ProgressPreference`.** A fresh session state means the script-level `SilentlyContinue` does not apply inside, so progress records pile up in `$ps.Streams.Progress` (20,000 in a repro) for output nothing renders. `Invoke-ModuleUpdate`'s script block sets it again explicitly
    - Terminating errors inside the script block surface from `EndInvoke` wrapped in a `MethodInvocationException`, so the `$ps.HadErrors` branch below it is only reached for non-terminating ones. The OneDrive locked-folder retry in `Update-AllModules` matches on the message text, which still contains the original `Cannot remove package path` string through the wrapper
- **Retry on transient network faults**: `Update-AllModules` and `Set-PinnedModuleVersions` call `Invoke-ModuleUpdateWithRetry`, never `Invoke-ModuleUpdate` directly. It makes up to three attempts, waiting 5s then 15s (`-RetryDelaySeconds`, not exposed in `config.json`), and logs each retry as WARN. A module that succeeds on a later attempt counts as a plain success: nothing lands in `Summary.ModulesFailed`, so the toast and the ping stay green. It exists because of a run where every pending update failed within seconds with `The SSL connection could not be established`. The task had fired via `StartWhenAvailable` right after the machine woke up, before the network had settled; the gallery was fine, but with no retry each module waited a week
    - **`Get-TransientNetworkFault` matches on message text because nothing else survives.** A failure inside the runspace arrives as `MethodInvocationException` -> `ActionPreferenceStopException` with no `InnerException` below that — PSResourceGet has already flattened the `HttpRequestException`/`SocketException` chain into one string. Measured against a dead proxy and an unresolvable host. Keep the pattern list narrow: a false positive costs 20s per module, and `404`/"not found" must never match
    - **Timeouts are not retried.** The module already spent its whole `ModuleUpdateTimeoutSeconds`, so retrying would multiply the runtime the timeout exists to bound. The wrapper rethrows the original `ErrorRecord`, so the callers' `catch [System.TimeoutException]` and the locked-folder message match both still work through it
    - **Worst case is bounded but not free**: a module that fails all three attempts costs about 20s of waiting on top of the failures themselves, per module. With the network fully down the update loop never gets that far, because `Find-GalleryModules` gives up first and no module is queued. Pins are different: they are enforced *before* the gallery lookup, so a missing pin does go through all three attempts
- **An unreachable gallery is a failure, not "up to date"**: `Find-PSResource` reports a network fault as a *non-terminating* error per module, so under `-ErrorAction SilentlyContinue` an unreachable PSGallery simply returns nothing. The run used to log `All modules are up to date` and send a **Success** ping, resetting the dead-man timer on a run that had checked nothing. Measured behind a dead proxy: about two seconds per installed module, several minutes in all, failing silently. `Find-GalleryModules` now owns the lookup:
    - **`SilentlyContinue` has to stay**, because "not on the gallery" is an everyday answer for a module installed from elsewhere. The two cases are told apart by `FullyQualifiedErrorId`: `PackageNotFound,*` means answered, anything else (`HttpRequestCallFailure` for a network fault) means not answered. **Error ids survive here even though they do not survive the isolated runspace** — do not "simplify" this to the message matching `Get-TransientNetworkFault` uses
    - **A probe runs before the bulk query**: one lookup of a hard-coded name, `Microsoft.PowerShell.PSResourceGet`. If the gallery gives no answer the bulk query is not sent. That is what took the unreachable case from several minutes to about half a minute, and what stops a hanging network from costing one timeout per installed module
    - **The probe tests reachability, not whether that module exists.** It is classified exactly like a bulk lookup, so `PackageNotFound` counts as an answer and the bulk query goes ahead. The first version used `-ErrorAction Stop` and treated any probe error as an outage, so unlisting or renaming that one module would have made every run report "Could not reach PSGallery". Verified against the real gallery with a probe name that does not exist
    - Unanswered lookups are retried on the same 5s/15s schedule, asking only about modules still without an answer. Whatever is left is counted in `Summary.ModulesUnchecked` (an int, with the reason in `Summary.GalleryFault`) and subtracted from `ModulesChecked`. `Get-SummaryFailures` includes it, which is what turns the toast, the ping and the closing line red
    - **An incomplete lookup is ONE failure, however many modules it left unchecked.** An outage is one thing going wrong; counting it per module made a single unreachable gallery read as one unsuccessful operation for every installed module. `Get-SummaryFailures` reports `Lookups` as 0 or 1, and the module count lives in `ModulesUnchecked`, the ERROR line and the toast ("150 not checked"). This holds for a partial failure too: three unanswered lookups are still one failure
    - A partial failure does not stop the run: modules that did get an answer are updated as normal, the ERROR line names the ones that did not, and "All modules are up to date" becomes "No updates found for the N modules that could be checked"
    - The module name in a `PackageNotFound` error exists only in the message text. If a future PSResourceGet rewords it, those modules stay pending and get counted as unchecked — but only in a run that already has unanswered lookups, so it errs toward reporting too much, never too little
- **Incremental summary saves**: `Save-Summary` is called after each phase (migration, updates, pruning), overwriting the same file. If the process is killed mid-run, the last completed phase's results are on disk
- **Progress suppression**: `$ProgressPreference = 'SilentlyContinue'` is set at script start — progress bars add significant overhead in non-interactive/scheduled task mode
- **Update optimization**: Bulk queries PSGallery via `Find-PSResource` to check for available updates, then only calls `Update-PSResource` for modules that actually need updating (avoids 150+ individual network calls)
- **PSResourceGet scope pitfalls**: `Get-PSResource` without `-Scope` defaults to CurrentUser only — after OneDrive migration, modules live in AllUsers so `-Scope AllUsers` is required. `Uninstall-PSResource` without `-Scope` can target ANY scope, potentially removing AllUsers copies instead of OneDrive copies. `InstalledLocation` on PSResource objects can return the modules root directory (e.g. `C:\Program Files\PowerShell\Modules`) instead of the version folder — the pruning fallback extracts the correct path from the PSResourceGet error message or constructs it from the module name + version
- **OneDrive handling**: When Documents is redirected to OneDrive via Known Folder Move, the main script detects this by checking `[Environment]::GetFolderPath('MyDocuments')` against OneDrive environment variables, then automatically targets AllUsers scope for updates and pruning. If modules installed by PSResourceGet are found in the OneDrive CurrentUser path, the prune phase logs a warning directing the user to run `Invoke-OneDriveMigration.ps1` — it does not delete them. The one-time migration itself is handled by `Invoke-OneDriveMigration.ps1` (separate script). `Remove-LockedModuleFolder` uses four-stage escalation for stubborn OneDrive files:
    1. Normal `Remove-Item -Recurse -Force`
    2. Strip OneDrive cloud-file attributes (`attrib -P -U -O`) + `cmd.exe rd /s /q` (handles reparse points/cloud placeholders)
    3. File-by-file deletion of whatever is deletable
    4. `kernel32.dll MoveFileEx` with `MOVEFILE_DELAY_UNTIL_REBOOT` — schedules remaining files for kernel-level deletion on next reboot
  - OneDrive cloud placeholders (reparse points) are the main blocker — files appear locally but are cloud-only stubs that standard file APIs reject with "Access denied"
  - Built-in modules (e.g., PackageManagement) that ship under `$PSHOME` are automatically skipped during pruning — PSResourceGet cannot uninstall these
  - When OneDrive is NOT detected, all behavior is identical to pre-migration versions
- **A module without `PSGetModuleInfo.xml` is not ours.** PSResourceGet (and PowerShellGet) write that hidden marker into every version folder they install. Without it `Get-PSResource` does not list the module, so this tool can neither update nor prune it. `Test-ManagedModuleFolder` checks for it, and both scripts leave unmarked modules where they are: the weekly script logs them at INFO (`Leaving N module(s) in OneDrive path alone, installed by another program`) instead of the WARN, and the migration neither copies nor deletes them
    - **`Microsoft.PowerToys.Configure` is the known case.** A per-user PowerToys install writes it to `Documents\PowerShell\Modules` and re-creates it on every PowerToys update (documented on Microsoft Learn; its version always equals the installed PowerToys). The old WARN came back week after week and could never be cleared by doing what it said
    - **The migration used to move it.** It copied the module to Program Files and deleted the original, and did so again after the next PowerToys update, leaving a row of orphaned copies that nothing would ever update or remove. Never copy a module this tool cannot maintain afterwards
    - The check is by marker, not by name, so any other program doing the same is handled without configuration. `-Depth 1` is deliberate: a marker deeper down belongs to a bundled dependency, not to the module
- **Prune by where a version is, not where it says it is.** `InstalledLocation` is written at install time and never corrected, so a module migrated out of OneDrive still reports its old OneDrive path while living in Program Files. The prune phase used to filter on that field to skip "OneDrive modules", which hid every migrated module from pruning for good: their old versions stayed while the log said `Found 0 modules with multiple versions`. `Resolve-ModuleVersionFolder` looks on disk under the AllUsers path instead, and the locked-folder fallback uses the folder it finds. It compares versions, not folder names, because the folder can be `6.1907.1.0` where PSResourceGet reports `6.1907.1`
- **Leftover version folders are expected, and harmless.** A module DLL loaded in an open PowerShell session cannot be deleted, so pruning that version leaves a folder of DLLs with no manifest. It happens now and then, to modules that are commonly loaded, such as an authentication module. PowerShell ignores a version folder without a manifest, so nothing loads from them. *Empty* version folders are a different thing: a one-time artifact of an early migration, not something the weekly run produces
- Modules are grouped by name; only the latest version is kept during pruning (or the pinned version, for pinned modules), plus the newest version of each line named in `KeepVersions`
- **`GroupInfo.Count` pitfall**: `$grouped = Group-Object ... | Where-Object {...}` returns a bare `GroupInfo` when exactly one group survives, and `$grouped.Count` then resolves to *that group's* item count instead of the number of groups. `Remove-OldModuleVersions` wraps the pipeline in `@()` for this reason — without it the log reported "Found 2 modules with multiple versions" for a single 2-version module
- Logs go to `$env:ProgramData\PSModuleMaintenance\Logs` with three file types: structured log, full transcript, and JSON summary
- **CMTrace-safe log wording**: CMTrace colors un-typed log lines red/yellow by scanning the text for `error`/`fail`/`warn` substrings, ignoring the `[INFO]` tag. Keep INFO/SUCCESS summary lines neutral so they don't appear as false errors — use `Unsuccessful:` not `Failed:`, and `No issues.` not `No errors.`. Only genuine `-Level WARN`/`-Level ERROR` lines should contain those words
- **The closing log line reports the outcome, it does not assume it.** It is `[SUCCESS] PSModuleMaintenance completed successfully` only when `Get-SummaryFailures` reports a `Total` of 0; otherwise it is a WARN: `completed with N unsuccessful operation(s) (config: v, lookups: w, updates: x, pins: y, prunes: z)`. It used to be unconditional, which could print "completed successfully" directly above `Healthchecks ping sent: Fail`
- The scheduled task uses `Interactive` logon type with "run with highest privileges" (runs hidden, requires user to be logged in but `StartWhenAvailable` catches up if missed) with a 4-hour execution time limit
- **The task registers `pwsh.exe` as a bare name, never a resolved path.** Task Scheduler re-resolves a bare executable name from PATH at every run (verified empirically before the change). A hard-coded path has broken a run before: PowerShell was reinstalled to a different directory, the registered `pwsh.exe` path stopped existing, and the task failed to start — producing no log, no toast and no summary, because nothing in the script ever ran. `Install-ModuleMaintenance.ps1` still calls `Get-Command pwsh.exe` but only to validate PATH resolution and print the current location. `Test-ScheduledTaskHealth` warns on every run if it finds a task whose `Execute` contains a directory separator, since a task registered by an older version of the installer keeps its baked-in path until re-registered
- **Healthchecks monitoring**: a dead-man's switch for the failure mode every other signal misses — a run that never *starts*. Toast notifications, `LastTaskResult` and the log files are all emitted by the script, so a script that never runs is silent (this has actually happened, when the task's hard-coded `pwsh.exe` path went missing during a PowerShell reinstall). Key constraints:
    - **The ping URL is a bearer secret and `config.json` is plain text**, easily copied, synced or shared, so it lives in the SecretManagement vault (`Get-Secret -Vault SecretStore`), never in config. The *full URL* is stored, not just the UUID, so self-hosted instances need no extra config. It is held in `$script:HealthchecksUrl` and never written to the log, transcript or summary
    - **`Get-HealthchecksUrl` runs before any update/prune work** — this script updates and prunes `SecretManagement`/`SecretStore` themselves, so the secret must be read while the module is still guaranteed loadable
    - **Soft-import, never `#Requires`**: a broken vault logs a WARN and maintenance continues. That is the fail-safe — no ping means the check goes overdue and Healthchecks alerts, so broken monitoring surfaces as a notification rather than as silence
    - **`-WhatIf` suppresses pings, which is the opposite of the logging convention below.** Bookkeeping writes pass `-WhatIf:$false` so dry runs still log; a ping must go the other way, because a success ping from a dry run would reset the dead-man timer and hide a genuinely missed run. `Invoke-RestMethod` has no ShouldProcess, so `Send-HealthchecksPing` checks `$WhatIfPreference` explicitly
    - The fail rule reuses the `$hasFailures` value already computed in `finally` for `NotificationMode: OnFailure`, which in turn comes from `Get-SummaryFailures`. The toast, the ping and the closing log line all go through that one function, so they can never disagree about what counts as a failure
    - Configure the check with a **Period** schedule (7 days, 1 day grace), *not* cron. The task uses `StartWhenAvailable`, so a sleeping machine catches up hours late, and cron with a tight grace would false-alarm every time
- `Invoke-PSModuleMaintenance.ps1` and `Invoke-OneDriveMigration.ps1` use `[CmdletBinding(SupportsShouldProcess)]` for `-WhatIf` support (`Install-ModuleMaintenance.ps1` does not — it is plain `[CmdletBinding()]`). Because `-WhatIf` sets `$WhatIfPreference` for the whole script scope, it cascades into ShouldProcess-aware cmdlets including the bookkeeping file writes. `Write-Log`'s `Out-File`/`Add-Content`, `Save-Summary`'s `Set-Content`, and the log-directory `New-Item` in both `Initialize-Logging` and `Invoke-OneDriveMigration.ps1` are called with `-WhatIf:$false` so logging and the JSON summary still run (and don't spam `What if: Performing the operation "Output to File"...`) during a dry run — only the real actions (copy/remove/update/prune) are gated by `-WhatIf`. The log directory is easy to miss because `%ProgramData%\PSModuleMaintenance\Logs` already exists in normal use; the gap only shows up on a dry run against a *fresh* `-LogPath`, where the missing directory silently suppresses both the log and the summary. `Start-Transcript` is deliberately left gated — the transcript is skipped during dry runs
